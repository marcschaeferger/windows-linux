# Windows

The Windows client predates the Linux port; most shared code was written for
it first. The Linux port (2026-11) moved Windows-specific code into
`*_windows.go` files without changing behavior (verified by comparing symbol
tables of the old and new binaries), upgraded Wails beta.25 → v3.0.0, and made
the update key/server overridable via ldflags.

## Startup flow (`main_windows.go`)

Double-clicking `Pangolin.exe` (no args):
1. `managers.RequestUILaunch()` writes the caller's session ID to
   `\\.\pipe\pangolin-manager-ui-launch`. If the service is running it
   launches the UI in that session and this process exits. Standard users never
   need SCM access or UAC in this path.
2. If the pipe isn't there: open SCM and the service with query/start rights
   only (`openManagerServiceForStart`), which standard users have. Service
   missing → re-run self elevated with `/installmanagerservice` (UAC prompt),
   which installs/starts the service (`managers.InstallManager`) and requests
   a UI launch with retry (15s). `InstallManager` only creates the service for
   an exe under Program Files, and never deletes and re-creates an existing
   one (it only starts it), so a loose copy of the exe can't take over the
   MSI's LocalSystem service.
3. Service stopped → try `service.Start()`, falling back to an elevated
   `net start`. Then request the UI launch.

The service (`/managerservice`, `managers/service_windows.go`):
- Enables `SeTcbPrivilege` so `WTSQueryUserToken` works.
- `startProcess(session)`: gets the user token, determines admin-ness (elevated,
  linked token, or Administrators member), creates 3 pipes, calls
  `IPCServerListen(... elevatedToken, SID, session)`, launches
  `Pangolin.exe /ui <fds>` with `CreateProcessAsUser` in the user's profile dir
  (`managers/uiprocess_windows.go`), waits for exit.
- Always-On: if the UI exits while Always-On is set for that SID, relaunch it.
- On WTS logon: if the user has open-at-login or connect-at-start
  (`launchUIAtLoginForSession` reads that user's LOCALAPPDATA), wait for
  `explorer.exe` in the session (≤60s) so the tray icon can be added, then
  launch.
- On WTS logoff: kill that session's UI, stop tunnels the session started.
- At start: installs a staged update first if appropriate (see
  [updates.md](updates.md)), then relaunches UIs recorded before an update,
  then handles sessions already signed in.
- IPC `Quit` (inherited from wireguard-windows) sends on `quitManagersChan`,
  which stops the service **and uninstalls it** (`UninstallManager`). Nothing
  in the UI calls `IPCClientQuit` today; the tray Quit stops tunnels and exits
  the UI only, and the service keeps running. On Linux nothing reads
  `quitManagersChan` at all. Don't wire up IPC Quit without knowing this.

`TaskbarCreated` so the tray icon comes back after Explorer restarts.

## MSI (`pangolin.wxs`, WiX 5)

- Installs `Pangolin.exe`, `wintun.dll`, icons, desktop + start menu shortcuts.
- `ServiceInstall` `PangolinManager` (auto start, `/managerservice`), started on
  install, stopped on install/uninstall, removed on uninstall.
- `MajorUpgrade` (downgrades refused). `Version` comes from `-d Version=X.Y.Z`
  (numeric only; CI strips `-rc.N`).
- Custom actions: install WebView2 via bootstrapper when not present
  (registry search for machine/user WebView2), clean up an orphaned manager
  service from older installs (`WixToolset.Util.wixext`).
- Build by hand: `scripts\build-msi.bat 1.0.3` on Windows.

## Release (CI: `.github/workflows/windows.yml`)

Tag `windows-X.Y.Z` (or `-rc.N`) →
1. `windows-build` (Ubuntu): `make build VERSION=…` cross-compiles
   `Pangolin.exe` (`-H windowsgui`, `production` tag).
2. `windows-sign` (windows-latest): jsign with DigiCert KeyLocker (secrets
   `SM_API_KEY`, `SM_CLIENT_CERT_FILE_B64`, `SM_CLIENT_CERT_PASSWORD`, var
   `SM_KEY_ALIAS`), fetches Wintun (pinned SHA256) and the WebView2 bootstrapper
   (Microsoft signature checked), builds MSI with WiX 5.0.2, signs MSI, verifies
   signatures + timestamps.
3. `release`: `scripts/generate-manifest.sh` + `sign-manifest.sh` with
   `UPDATE_SIGNING_KEY` → `windows-latest.sig`, draft GitHub release.
4. Manual: publish the release, upload `windows-latest.sig` to
   `s3://static.pangolin.net/windows-client/latest.sig` (owner does this; see
   [updates.md](updates.md#update-server)).

The repo was renamed `fosrl/windows` → `fosrl/windows-linux` on 2026-11-05.
Old manifests on S3 still point at `github.com/fosrl/windows/releases/...`;
GitHub redirects them. Rewriting them would require re-signing (the URL is
inside the signed text). A dry-run script for that was written
(`scripts/rewrite-manifest-urls.sh`) but is **not in the repo**; its work dirs
are `../manifest-rewrite-2026110*`. It has not been uploaded.

## Adding a Windows feature: checklist

- Put Win32/registry/service code in a `_windows.go` file, and give Linux a
  same-named stub or real implementation in `_linux.go` (even if it just
  returns an error), so shared code compiles on both.
- If the manager needs to read something per-user, use the session's token
  (`localAppDataForSession`), never the service's env.
- Admin-only actions: check `s.elevatedToken != 0` in the `ManagerService`
  method; on Linux the same field means root/sudo/wheel/admin.
- Cross-compile check from Linux: `GOOS=windows go vet -unsafeptr=false ./...`
  and `GOOS=windows go build -tags production -o /dev/null .`. Nobody can run
  Windows from this Linux machine, so ask the owner to smoke-test behavior.
- Frontend strings: `isLinux` in `ui/frontend/src/lib.ts` (user-agent test)
  switches wording, so Linux text doesn't mention Windows. Check both before
  changing user-facing text. The UI imitates the macOS client's look and
  flows (many comments reference macOS Swift files).
